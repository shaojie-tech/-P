# 团队协作规范（面试官小P 项目版）

> 核心原则：**源码归 Git，协作归 WorkBuddy 项目，外部服务归连接器。** 三者不要混。
>
> 本项目实际取值：仓库 <https://github.com/CodeStar918/-P> · 本地目录 `D:\projects\智能面试`

---

## 一、职责边界

| 层 | 承载什么 | 不承载什么 |
|---|---|---|
| Git 仓库（GitHub） | 源码、分支、PR、CI、issue | 需求讨论、会议结论、验收标准 |
| WorkBuddy 项目 | 项目指令、项目资产（文档）、任务、任务流转 | 源码文件、密钥、个人数据 |
| 连接器 | Git 平台、TAPD、腾讯文档等外部服务 | — |

**唯一代码真源 = Git。** 资产库不是版本控制系统，没有 diff、没有冲突合并。同一份代码同时存在于两处，必然发散。

本项目对应关系：源码真源 = `https://github.com/CodeStar918/-P`；技术约定 = 仓库内 [AGENTS.md](../AGENTS.md)（**不是**资产库）。


## 三、资产库存放清单

进入方式：项目详情页 → 顶部「资产」标签。

### 3.1 先立判据：一份文档该不该进资产库？

**唯一判据：它是否需要与代码同步演进？**

| 答案 | 去向 | 原因 |
|---|---|---|
| **是**（改代码就得改它） | 留在 **Git 仓库**，走 PR | 需要 diff、评审、回滚；进资产库会多出第二个真源 |
| **否**（与代码版本无关） | 放 **资产库** | 跨人可检索、可注入任务上下文 |

行业依据：**SSOT（单一事实来源）** + **Diátaxis 文档分类法**（按用途分：教程 / 操作 / 参考 / 解释，而非把 docs 目录整体镜像一份）。资产库是精选知识库，不是 docs 的备份盘。

### 3.2 应该放资产库（附本项目现状）

| 内容 | 承载什么 | 行业依据 | 本项目现状 |
|---|---|---|---|
| `requirements/` | PRD、需求变更记录 | 需求可追溯 | ❌ 未建 |
| `docs/acceptance.md` | 验收标准 | 可验证交付 | ❌ 未建 |
| `docs/onboarding.md` | 团队协作上手（怎么领任务、怎么流转） | Diátaxis · Tutorial | ⚠️ 技术上手已由 README「快速开始」覆盖，团队流程部分缺 |
| 会议纪要、评审结论 | 决策留痕 | 决策可追溯 | ❌ 未建 |
| `INDEX.md`（可选） | 指向 Git 侧文档的**指针**，不做副本 | SSOT 防分叉 | ❌ 未建 |

### 3.3 应该留在 Git，**不要**放资产库（附本项目现状）

| 内容 | 为什么必须留 Git | 当前路径 | 现状 |
|---|---|---|---|
| 开发约定 | 改代码就要改约定 | `AGENTS.md` | ✅ 已有 |
| 版本变更 | 与 tag / PR 一一对应 | `CHANGELOG.md` | ✅ 已有 |
| 缺陷清单 | 与修复提交绑定 | `BUG_REPORT.md` | ✅ 已有 |
| 用户文档 | 功能一变就过期 | `README.md`、`TUTORIAL.md` | ✅ 已有 |
| 界面设计规范 | 与前端实现同步 | `docs/design-spec.md` | ✅ 已有 |
| CI / 部署配置 | 配置即代码 | `.github/workflows/`、`deploy/` | ✅ 已有 |
| **架构决策记录** | 决策与代码版本绑定，ADR 业界通例是入库随 PR | `docs/adr/` | ❌ **最该补的一环** |
| 数据模型与迁移史 | 事实来源是迁移代码本身 | `app/core/db.py`（`user_version = 8`） | ⚠️ 目前只能读代码 |
| 接口契约 | FastAPI 自动生成 OpenAPI | `/openapi.json`、`/docs` | ⚠️ 见下方第 1 条修正 |
| 协作规范 | 规范会演进，需要历史与 diff | `docs/TEAM_COLLABORATION.md` | ✅ 本文 |

### 3.4 对原清单的三处修正

原清单把 `docs/api.md`、`docs/schema.md`、`docs/architecture.md`、`docs/adr/` 一并列进资产库。按 3.1 的判据，这四项都需要与代码同步演进，**放进资产库会制造双真源**。具体处理：

1. **`docs/api.md` 建议不建。** 本项目接口契约由 FastAPI 自动生成的 OpenAPI 承载——服务起来后访问 `/docs` 或 `/openapi.json` 即得。它是**活契约**，改了路由立刻同步；手写一份 `api.md` 只会滞后，并误导读它的人。约定改为：**契约以自动生成为准**。
2. **`docs/adr/` 应进 Git，不是资产库。** 架构决策记录（ADR）记录的是"当初为什么这么选"，与代码版本强绑定，业界通例是随代码入库、跟着 PR 走。本项目现在的决策散落在 `BUG_REPORT.md` 的说明段与工作日志里（例如"语音为什么不直接上 Realtime 模型"），**这是当前最该补的一环**。
3. **`docs/architecture.md` 暂不需要单独建。** `AGENTS.md` 的「目录约定」已覆盖模块职责与分层（routers / agent / stores / services / core / crawler）。信息已经存在，再建一份必然发散。真到了现有章节装不下的规模，再拆出去。

### 3.5 不要放

- 完整源码仓库、zip 包
- `node_modules/`、`dist/`、`__pycache__/`
- `.env`、`*.pem`、`credentials.json`、任何密钥
- 个人文件、临时草稿

### 3.6 为什么

项目资产在每次创建任务时会以 **reference 形式注入上下文**。资产库越杂，检索到的噪声越多，AI 回答质量越差，还容易把敏感文件带进对话。**它是一份精选知识库，不是文件回收站。**

比"噪声"更隐蔽的风险是**双真源**：同一份内容 Git 与资产库各一份，PR 改了 Git 里那份，资产库那份还是旧的——AI 检索到旧版会给出错误答案，而且没人会发现。这正是 3.1 那条判据存在的理由。

配额：默认 5 GB（依托腾讯网盘）。

## 四、任务与流转

- **一人一任务**：每个成员在项目里开自己的任务，产物自动归属该项目。
- **交接用「任务流转」**：任务对话页顶栏 → 流转图标。系统自动打包：
  - 任务产物（本次生成的所有文件）
  - 任务进度摘要（自动生成的执行过程总结）
  - 自定义字段（标题、描述、处理人、状态、截止日期）
  - 附加附件
- 接收方拿到完整上下文，不需要重新交代背景。**这是跨人协作的核心机制，比在群里贴链接有效得多。**
- 状态取值：待开始 / 进行中 / 已暂停 / 已完成。

## 五、连接器配置（重点坑）

| 类型 | 团队成员可用性 |
|---|---|
| 公共授权连接器 | 全部成员可用，协作任务中正常工作 |
| 个人授权连接器 | **在协作任务中全部禁用**，仅本人在单人任务中可用 |

**结论：团队公共依赖的服务（Git 平台、TAPD、腾讯文档、企微）必须配置为公共授权。** 否则会出现「我在自己会话里明明能用，一进项目任务就报无权限」的情况——这不是 bug，是设计。

另注：个人授权连接器的票据只保存在成员本地，不会上传云端；项目配置（指令 / Skill / 专家 / 连接器）存在云端，**全员共享可见**。

## 六、成员准入流程

1. 项目管理员在项目详情页右上角点「邀请」，复制链接。
2. 被邀请人打开链接 → 填写申请备注 → 提交。
3. 管理员在消息中心审批。
4. 准入后该成员可访问项目指令、项目资产、项目任务。

任何成员都能发起邀请，但**放人进项目的决定权在管理员**。

## 七、自动化注意

项目自动化在**创建者本人会话中运行，仅创建者可见**。团队成员若都依赖某条自动化，需要各自创建，或把它做成独立 Skill 分发。

## 八、新人上手（写进 onboarding.md）

```
1. clone 仓库到本地，切换到指定开发分支
2. 读仓库内文档：AGENTS.md（技术约定）、docs/design-spec.md（界面规范）、README.md（运行方式）
3. 本地起服务（接口契约看服务起来后的 `/docs`，由 FastAPI 自动生成）
   cd frontend && npm install && npm run build && cd ..
   python -m uvicorn app.main:app --host 127.0.0.1 --port 8765
4. 在 WorkBuddy 项目里领一个任务，产物放 outputs/
5. 完成后走任务流转交给 review 人
```
